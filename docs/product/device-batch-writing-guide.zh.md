# Multiverse Console Batch 共创写作与内容设计指南

> 文档用途：指导真人作者、编辑、AI 共创者为不同设备 Batch 设计并撰写从首次发布、开放申领、分阶段发放到 Console 出货及进入运行档案的完整内容。
> 配套文档：[Multiverse Console 批次探索、申领与等待体验](./device-batch-experience.zh.md)
> 本文只讨论内容设计、叙事连续性和写作质量，不讨论产品优先级或技术实现。

---

## 1. 写作者到底在创作什么

一个 Batch 不是一篇商品介绍，也不是按月连载但互不相关的世界观短篇。

写作者要共同维护的是一份**持续变化的行动档案**：

1. 组织在一个具体地点发现一批设备；
2. 团队通过调查、清点、修复和测试逐步确认事实；
3. 成员开始关注或申领这批设备；
4. 不同 Pack 按该 Batch 独有的节奏发放；
5. 成员通过讨论、图片和投票参与部分决定；
6. 每次决定和发现都在后续报告或实体物件中产生结果；
7. Console 最终送达后，行动转为长期运行档案。

所有内容都应服务于这条主线：

> **前一次发现提出问题，下一次行动处理问题，成员参与影响过程，后续内容展示结果，实体 Pack 或 Console 让结果真正落地。**

如果一段内容不能改变用户对“现在发生了什么、为什么值得等待、下一步是什么”的理解，它通常不值得发布。

## 2. 六条不可破坏的写作原则

### 2.1 先有行动，再有气氛

沉浸感来自具体的人、地点、物件、动作和时间，而不是大量神秘形容词。

推荐：

> 7 月 18 日，Weile 在第二层机架中拆出了 17 个结构相同的调谐器。其中 5 个无法保持回传信号。

避免：

> 一批不可思议的远古装置正在黑暗中等待被唤醒。

### 2.2 每个 Batch 必须有自己的“内容发动机”

更换地点、设备名和负责人，不等于创造了一个新 Batch。每个 Batch 至少需要一个独有的持续矛盾，例如：

- 数量很多，但不同设备只能接收特定方向的信号；
- 设备完整，但天线零件散落在不同区域；
- 外壳损坏严重，内部记录却异常完整；
- 同批设备出现两种相反的校准结果；
- 前置使用者留下了一组不完整的操作影像；
- 设备能运行，但现有电源方式无法稳定复现。

这个矛盾应贯穿现场报告、投票、Pack 内容和最终 Console，而不是只写在首次介绍里。

### 2.3 事实层必须比故事层更清楚

可以保留悬念的内容：

- 设备最初由谁使用；
- 某个信号意味着什么；
- 零件为何出现在现场；
- 前置记录是否完整可信；
- 团队正在验证的来源假设。

不能用悬念模糊的内容：

- Batch 总价和实际收费；
- 已确认数量和剩余名额；
- Pack 数量及实际内容；
- 预计寄送日期或日期范围；
- 哪个 Pack 包含 Console 本体；
- 物流、配送范围、延迟、退款和售后；
- 用户是否已经成功申领。

事实状态统一分为三种：

- **已确认**：有明确证据或已经成为履约承诺；
- **当前估计**：基于现有调查得出的范围或预期；
- **待验证**：故事中的假设、传闻或未完成判断。

作者不得把“待验证”写成确定事实，也不得擅自修改已经公开的履约承诺。

### 2.4 所有内容必须具有连续因果

每次写作前先回答：

1. 这条内容承接了哪一个已知事件？
2. 它新增了什么事实、问题或决定？
3. 它会影响哪个 Pack、节点或成员行动？
4. 后续哪条内容负责回收它？

没有回收计划的谜团不要无限增加。每个 Batch 同时保持 1–3 个未解决问题通常已经足够。

### 2.5 等待期不是用故事掩盖物流

内容可以让等待有意义，但不能拿 NPC 剧情代替真实进度。

当出货发生变化时，更新必须同时包含：

- 哪个节点发生变化；
- 原预计时间与新预计时间；
- 已确认的原因；
- 当前采取的措施；
- 下一次更新时间；
- 对用户各 Pack 或 Console 的实际影响。

角色口吻可以保留，但事实信息要先被用户快速读懂。

### 2.6 到货不是故事终止

Console 发出后，Batch 的写作目标从“恢复与交付”转为“运行与共同记录”：

- 发布恢复行动总结；
- 记录最终发放数量；
- 收录持有者首次启动内容；
- 对此前投票、线索和 Pack 做最终回收；
- 保留少量维护、信号和成员发现更新。

### 2.7 完整故事先行

Batch 创作的第一责任人是提供原始创意的作者，不是负责拆解内容的 AI。开始平台适配前，作者应先用自己的
语言提供一个从发现、设备特征、前主人、当前问题到核心悬念的完整故事。这个故事可以保留未知和模糊处，
但不能只是一组等待 AI 自由补全的关键词。

AI 的第一轮工作不是扩写页面、帖子和投票，而是忠实拆解原稿：

1. 保留原稿的前提、因果顺序、设备身份和结尾钩子；
2. 区分作者明确确认的事实、故事中的判断或相信、以及刻意未解的问题；
3. 提炼设备特征、来源线索、修复矛盾、独有发现和一句话内容发动机；
4. 标出平台规则与原稿之间需要作者决定的冲突；
5. 只给出最小的阶段节奏，不立即生成完整内容地图。

第一轮产物称为“故事适配稿”。只有作者确认故事适配稿没有改变原意后，才进入发布计划、内容节点、
Pack 对应和投票设计。作者对原始创意拥有最终决定权；AI 负责结构化、连续性检查和平台节奏，不默认增加
支线、角色、神秘事件或互动数量。

### 2.8 两个人工审核门槛

Story Lab 的人工审核分为两个阶段，任何 AI 结果都不能越过审核门槛直接发布：

1. **Review Gate 1 — 故事结构审核**：作者和 Architect 审核英文故事适配稿，确认事实、判断、未知、
   核心矛盾、故事发动机与四阶段节奏均忠实于原稿；状态依次为 Draft、In Review、Changes Requested、
   Approved。
2. **Review Gate 2 — 单条内容审核**：只有 Gate 1 批准后，AI 才能生成英文发布内容和推荐时间；每一条
   内容分别保存、送审和批准，只有 Approved 内容可以设置真实排期或立即发布。

AI 推荐的日期和时间只是编辑建议，不构成排期。实际排期由 Architect 单独确认。若 Gate 1 的原始故事或
结构化适配稿发生变化，所有尚未发布的下游内容自动进入 Needs Re-review，并清除原排期；已经发布的记录
保持不可变，以保留真实发布历史。

建议的首次输入格式：

```text
Batch / 发现地点：
从头到尾的完整原始故事：
设备不可改变的外观与功能：
故事中明确是“相信 / 据说 / 可能”的部分：
目前刻意不知道的部分：
AI 不得修改或新增：
```

## 3. 动笔前必须建立 Batch Bible

故事适配稿经作者确认后，任何作者或 AI 在撰写单条页面内容之前，都应先获得同一份 Batch Bible。
它是平台适配和发布阶段的内容真相源；作者确认的完整原稿仍是创意来源。

### 3.1 基础身份

| 字段 | 要求 |
|---|---|
| Batch 名称 | 能被记住，不与地点或设备类型重复堆叠 |
| Batch Code | 统一、稳定，不在不同页面变体 |
| 发现地点 | 城市、国家；必要时增加场所类型 |
| 当前状态 | 探测中 / 可申领 / 发放中 / 运行中 |
| 发现日期 | 明确日期或已确认范围 |
| 最近更新时间 | 对应真实发布节点 |
| 核心负责人 | 姓名、头像、职责、语气 |

### 3.2 商业与履约事实

| 字段 | 规则 |
|---|---|
| Batch 总价 | 当前产品规则为每个 Batch 一个总价；不同 Batch 可以不同 |
| 数量 | 区分发现数量、可恢复数量、可申领数量和已申领数量 |
| Pack 数量 | 可按 Batch 配置，不默认三次 |
| Pack 时间 | 使用准确日期或日期范围；不确定时写明更新条件 |
| Pack 内容 | 写实际会寄出的内容，不以气氛词替代 |
| Console 所在 Pack | 必须明确 |
| 配送与运费 | 与实际政策一致 |
| 取消、退款、售后 | 不由叙事作者自行编造 |

### 3.3 内容发动机

用一句话写清这个 Batch 的持续矛盾：

> 我们发现了 ______，但 ______，因此团队必须在 ______ 之前完成 ______。

再列出：

- 三个已经确认的事实；
- 两个仍待验证的问题；
- 一个最终应在 Console 出货前被回答的核心问题；
- 一个可以延续到运行阶段的长期问题。

### 3.4 物件词典

列出本 Batch 会反复出现的 5–10 个具体物件名称，并固定用词。例如：

- 定向天线片；
- 调谐组件；
- 现场编号卡；
- 回传测试记录；
- 修复外壳样本；
- Console 电源接口。

不要在不同作者手中把同一个物件轮流写成“天线碎片”“接收芯片”“神秘零件”，除非剧情明确说明认知发生了变化。

### 3.5 Batch 视觉身份卡

每个 Batch 的 Console 应拥有可辨认的配色与外观处理，但仍然属于同一种 Multiverse Console，
不能只靠更换背景色制造差异。当前产品规则是：**不同 Batch 的配色与外观不同，同一 Batch 内的
所有 Unit 配色、材质表现和外观完全一致。** 个体历史差异通过 Unit 档案和使用记录表达，不通过
外壳随机变化表达。故事作者在规划 Batch 时应与视觉创作者共同确定：

- 不可改变的 Console 基础轮廓、核心部件和操作方式；
- 主色、辅助色、信号灯颜色及各自出现的位置；
- 外壳材质、表面处理、磨损程度和修复痕迹；
- 旋钮、屏幕、铭牌、接口等关键部位的 Batch 特征；
- 现场环境如何影响该批设备的外观，而不是事后附会一套配色；
- 同一 Batch 内 Unit 档案、历史与信号记录允许出现的个体差异；
- 禁止出现的颜色、材质、装饰或结构变化；
- 当前素材属于实物事实、制作方案、概念设计还是生成示意。

视觉身份必须与内容发动机形成因果关系。例如，外壳褪色可以来自已确认的存放环境，替换面板可以来自
一次修复决定，成员投票也可以影响非安全性的表面处理；不要为了制造限量感而添加与行动无关的装饰。

故事作者向视觉实现者交接时，至少应提供：

```text
Batch：
视觉概念一句话：
Console 不可改变的基础特征：
主色 / 辅助色 / 信号色：
材质与表面处理：
关键识别部位：
磨损与修复依据：
Unit 档案与记录差异范围：
必须延续的故事线索：
禁止修改或新增：
参考影像及其素材性质：
当前需要的输出：概念图 / 产品图 / 细节图 / 页面素材 / 实物制作说明
```

视觉方案一旦用于公开影像或实体制作，其稳定特征应进入事实账本。后续调整必须说明是概念迭代、
修复结果还是制作变化，不能静默替换已经成为用户认知或履约承诺的外观。

### 3.6 角色卡

每个主要角色包含：

- 名称与头像；
- 组织身份和本次职责；
- 已知背景；
- 只由该角色掌握的信息；
- 说话长度、语气和常用观察方式；
- 不会做或不会说的事情；
- 与其他角色的工作关系。

一个 Batch 建议保持 1 位核心负责人和 1–2 位辅助角色。新角色只在承担明确功能时出现。

### 3.7 影像计划

在 Batch 发布前规划至少四类素材：

1. 建立地点和现场关系的广角影像；
2. 展示设备或零件细节的近景影像；
3. 展示负责人正在行动的过程影像；
4. 展示测试、修复或包装结果的前后对比影像。

同时确定哪些内容适合照片、组图、短视频或成员投稿。文字不能长期承担本应由证据影像完成的工作。

## 4. 从发布到出货的内容章节

Batch 对用户公开三个大章节，但写作上按四个工作阶段组织。

### 4.1 探测中 / UNDER SURVEY

#### 写作目标

让用户相信“组织确实发现了一批值得继续观察的设备”，并愿意关注后续，而不是立刻购买。

#### 首次发布必须回答

- 在哪里发现；
- 最初由谁发现或报告；
- 现场目前看到了什么；
- 哪些信息已经确认；
- 哪些信息仍然未知；
- 团队接下来要做什么；
- 下一次预计何时更新；
- 用户关注后会收到哪些通知。

#### 推荐内容组合

- 1 张主现场图；
- 2–5 张细节或环境组图；
- 1 段 15–60 秒短视频；
- 1 份 120–250 字的首次现场报告；
- 1 条负责人的短留言；
- 1 个明确的下一里程碑；
- 可选的公开讨论问题。

#### 探测期更新类型

- 信号源或现场范围确认；
- 可恢复数量初估；
- 首台设备通电；
- 新零件或前置记录被发现；
- 某个原有假设被推翻；
- 修复方案得到验证；
- 申领数量即将确认。

探测期每条更新都要减少一种不确定性，或合理地揭示一个会影响后续行动的新问题。

#### 不应出现

- 未确认就公布精确库存；
- 提前暗示用户已排队或锁定名额；
- 用虚假倒计时推动关注；
- 连续发布只有氛围、没有调查进展的内容；
- 在没有 Pack 和价格事实时写申领承诺。

### 4.2 可申领 / CLAIM OPEN

#### 写作目标

把一次调查进展转化为清晰的加入邀请：用户既理解这个 Batch 的意义，也准确理解自己购买了什么。

#### 开放公告必须包含

- 已确认的可恢复或可申领数量；
- Batch 总价；
- 当前供给状态；
- Pack 总数；
- 每个 Pack 的内容和预计窗口；
- 哪个 Pack 包含 Console；
- 预计完成时间；
- 申领后立即解锁的数字体验；
- 关注与申领之间的区别。

#### 开放公告的推荐结构

1. **结论**：本 Batch 已达到开放条件；
2. **证据**：哪些调查或测试支持这个结论；
3. **数量**：本次实际开放多少台；
4. **发放计划**：用户会按怎样的节奏收到什么；
5. **下一行动**：申领，或继续关注。

开放申领不是促销文案。少用“独家”“史诗”“错过不再”等词，不编造紧迫性。

#### 申领后的第一条内容

用户完成付款后，应立即看到：

- “你已被登记为本批次持有者”；
- 当前 Unit 已分配或待分配状态；
- 全部 Pack 的简化时间线；
- 下一件确定会发生的事；
- 当前负责人；
- 最近 3–4 条讨论或进展；
- 一个明确的首次参与动作。

首次参与动作可以是自我介绍、确认地址、查看 Pack 01、回答一个不影响履约的小问题，但同屏只突出一个。

### 4.3 分批发放中 / DISTRIBUTION IN PROGRESS

#### 写作目标

用可验证的行动、实体 Pack 和成员参与维持连续体验，同时准确解释制造与物流进度。

每个 Pack 建议形成一个完整的小循环：

1. **预告**：为什么下一 Pack 此时出现；
2. **准备**：团队正在整理、测试或包装什么；
3. **寄出**：实际内容、窗口和物流事实；
4. **收到**：成员上传图片或反馈；
5. **回收**：负责人解释它与后续 Console 的关系；
6. **推进**：进入下一阶段或提出下一问题。

#### 两个 Pack 之间至少有一个有意义的数字节点

可以是：

- 新的现场报告；
- 一次测试视频；
- 对上次投票结果的执行说明；
- 成员开箱图精选；
- 下一 Pack 的细节预告；
- 一项需要成员判断的非安全性选择。

不要为了填满日历而发布。节点由事件驱动，不要求所有 Batch 拥有相同更新频率。

#### 投票写作规则

投票发布前必须明确：

- 为什么需要这个决定；
- 用户真正能改变什么；
- 哪些条件不可改变；
- 选项之间的实际差异；
- 截止时间；
- 结果将在何时、以何种形式出现。

投票结束后必须发布：

- 结果；
- 负责人回应；
- 采用或无法采用的原因；
- 结果将影响的报告、Pack 或 Console 细节。

不能回收的投票不要发起。

#### 延迟更新模板原则

第一句话先写事实：

> Pack 02 的预计寄出窗口由 8 月 12–20 日调整为 8 月 26 日–9 月 3 日。

随后解释：

- 哪项测试或供应环节尚未完成；
- 已完成了哪些工作；
- 对其他 Pack 是否有影响；
- 用户是否需要行动；
- 下一次更新时间。

不要让 NPC 先说几段故事后才在末尾透露延期。

### 4.4 Console 出货与运行中 / ACTIVE IN FIELD

#### 写作目标

让 Console 出货成为此前所有内容的结果，而不是普通物流通知；同时完成商业交付并开启长期档案。

#### Console 出货前

- 回收核心未解问题；
- 展示最终测试或校准证据；
- 明确 Unit 分配方式；
- 重申包裹实际内容；
- 发布最终地址确认或必要操作；
- 说明寄出窗口和物流入口。

#### Console 寄出公告

公告应同时包含：

- 本 Batch Console 已开始寄出；
- 实际寄出数量；
- 用户如何查看自己的物流；
- 预计到达范围；
- 首次启动或安全说明；
- 收到后建议记录什么；
- 批次何时转为运行中。

#### 运行总结

总结不是重复时间线，而是回答：

- 最初的问题是什么；
- 团队和成员做出了哪些关键决定；
- 哪些假设被证实或推翻；
- 各 Pack 如何组成最终体验；
- 有多少台设备进入运行；
- 哪些问题将继续由持有者记录。

运行阶段的低频内容可包括维护说明、成员信号记录、设备陈列、跨地区共同现象和周年归档。

## 5. 各内容类型的写法

### 5.1 列表页 Batch 摘要

只回答四件事：

- 这是什么；
- 在哪里；
- 现在处于什么状态；
- 用户下一步能做什么。

推荐长度：

- 标题：2–5 个词；
- 当前进展：20–45 个中文字；
- 行动按钮：2–6 个字。

列表卡片不写完整负责人履历、Pack 清单、当前与下一阶段的重复说明或长篇世界观。

### 5.2 首屏状态文案

首屏信息顺序：

1. Batch 名称和地点；
2. 当前状态；
3. 一句最新事实；
4. 主操作；
5. 多图或视频证据。

避免在同一区域重复 Batch 名、设备名、组织名和状态名称。

### 5.3 现场报告

推荐结构：

**标题：一个发生了的具体变化**

> 12 台接收器完成第二轮回传测试

**正文：**

1. 从上一节点承接；
2. 本次做了什么；
3. 得到了什么结果；
4. 对 Pack、时间或下一调查的影响；
5. 尚未解决的问题；
6. 是否需要成员回应。

推荐长度为 150–450 字。信息较多时使用小标题或项目符号，不靠超长段落制造“档案感”。

### 5.4 负责人留言

负责人留言适合短、具体、带有个人观察：

> 今天我们第一次让三台设备保持了完全相同的回传节奏。剩余差异集中在天线连接处，我会在周五的报告中展示拆解对比。

它不应只是：

> 工作还在继续。感谢大家耐心等待。

主页面只显示头像、昵称和一句最新留言；完整身份信息进入二级内容。

### 5.5 NPC 讨论帖

每条 NPC 发言至少承担一种功能：

- 补充现场观察；
- 回答成员问题；
- 纠正错误理解；
- 提出下一项判断；
- 公布投票或结果；
- 解释变化。

NPC 不冒充真实购买者，不发布虚假的开箱或物流体验。

讨论预览只展示最近 3–4 条有价值内容。完整留言板纵向排列，方便阅读上下文；不为单条帖子创建独立 URL。

### 5.6 Pack 描述

每个 Pack 的文字必须分开写：

- **实际包含**：用户会收到的物件；
- **行动关系**：这些物件为什么在这个阶段出现；
- **预计窗口**：真实日期或日期范围；
- **当前状态**：未来、准备中、已寄出、已完成；
- **下一连接**：它如何通向下一个 Pack 或 Console。

避免把普通周边包装成具有实际设备功能的零件。能否安装、是否可用、是否只是档案物件必须准确。

### 5.7 组图与视频说明

每个媒体项需要：

- 拍摄日期；
- 地点或场景；
- 图中主体；
- 它证明或补充了什么；
- 必要时说明是否为复原图、示意图或叙事化素材。

组图推荐顺序：

1. 建立场景；
2. 关键主体；
3. 细节证据；
4. 人物行动；
5. 结果或变化。

视频标题描述内容，不使用“绝密影像”“泄露片段”等空洞噱头。封面应能独立说明主体。

### 5.8 通知和邮件

通知只围绕重大事项发送。标题直接写变化：

- Cairo Batch 01 已开放申领；
- Pack 02 已进入准备阶段；
- 调谐方案投票将在 48 小时后结束；
- Console 寄出窗口已更新；
- 你的 Unit 已开始运输。

正文说明为什么收到、发生了什么、用户是否需要行动，并直接链接到相应 Batch 节点。

## 6. 内容节奏的配置方法

不同 Batch 可以拥有不同 Pack 数量、阶段间隔和总时长，因此内容计划不能套用固定“三个月三次寄送”。

先确定实体时间线，再插入数字节点：

| 节点 | 必需内容 |
|---|---|
| Batch 首次发布 | 现场证据、已知/未知、负责人、下一里程碑 |
| 重大探测结果 | 新证据、判断变化、下一行动 |
| 开放申领 | 数量、总价、全部 Pack、Console 时间 |
| 申领成功 | 持有者身份、下一件事、内部入口 |
| 每个 Pack 前 | 原因、内容预告、预计窗口 |
| 每个 Pack 寄出 | 实际内容、物流事实、成员引导 |
| Pack 之间 | 报告、结果、投票或成员精选至少一种 |
| Console 出货前 | 最终测试、Unit 分配、地址与时间确认 |
| Console 寄出 | 物流、到货、首次启动指引 |
| 运行中 | 总结、结果回收、长期记录方向 |

建议为每个内容节点记录“最迟发布日期”和“触发条件”。如果触发条件尚未发生，不要仅为满足原日历而编造进展。

### 6.1 在故事适配确认后建立内容地图

不要在作者刚提交完整原稿时就展开全部页面、帖子和投票。此时只需要交付故事适配稿和最小阶段节奏，
让作者先确认原意、事实边界、内容发动机与核心悬念。

故事适配稿和 Batch Bible 均获确认后，再一次性规划从首次发现到运行总结的全部已知内容节点。每个节点至少记录：

- 节点编号、阶段、内容类型与目标受众；
- 它承接的上一事件；
- 本次新增的事实、决定或问题；
- 对 Pack、Console、日期或成员理解的影响；
- 用户是否需要行动；
- 它提出的问题将在何处回收。

完整地图是内部可修改的策划基线，不应默认全部展示在故事适配界面，也不是对外承诺。新证据、制作变化或作者意见可以调整节点内容和顺序，
但调整时必须同步连续性账本，并为已经公开的线索保留新的回收位置。

只有具备真实决策意义的预定投票才进入内容地图，并写明触发条件、可改变范围、不可改变边界、选项差异、
结果公告和实体或数字结果的落点。一个阶段没有需要成员决定的事情时，不必设计投票。

## 7. 连续性账本

多人或多 AI 共创时，必须维护一份结构化连续性账本。

### 7.1 事实账本

记录所有已经公开的：

- 数字；
- 日期；
- 人名与职责；
- 地点；
- 设备和零件名称；
- Pack 内容；
- 当前状态；
- 履约承诺。

已发布事实不能被新作者静默覆盖。发生变化时必须以新事件解释。

### 7.2 问题账本

每个未解问题包含：

- 首次出现时间；
- 当前已知证据；
- 负责人；
- 计划在哪个节点推进；
- 最迟在哪个节点回收；
- 回收后影响什么。

### 7.3 决策账本

每次成员投票或团队决定记录：

- 决策原因；
- 可选范围；
- 最终结果；
- 谁作出决定；
- 后续在哪份报告、哪个 Pack 或哪台 Console 上体现。

### 7.4 素材账本

记录每张照片、每段视频：

- 文件和版权状态；
- 拍摄或制作日期；
- 对应事件；
- 是否已经公开；
- 是否允许再次使用；
- 是否为真实记录、复原、示意或生成素材。

## 8. 角色与声音

角色之间的差异来自观察重点，而不是夸张口癖。

### 负责人 / Field Lead

- 关注行动整体、风险和下一里程碑；
- 负责重大更新、延期和最终总结；
- 语气稳定、准确，不回避坏消息。

### 修复或测试成员

- 关注具体结构、测试差异和技术发现；
- 使用用户能理解的必要术语；
- 提供影像、对比和判断依据。

### Archive Office

- 关注记录、命名、材料整理和投票结果；
- 负责阶段存档与成员贡献收录；
- 不承担物流客服角色。

### Signal Desk

- 关注影像、信号和使用记录；
- 适合发布短视频、首次启动和运行期观察；
- 不对未经验证的来源作确定结论。

所有角色都遵循同一事实账本。角色差异不能导致履约信息互相矛盾。

## 9. AI 共创的标准工作流

AI 共创分成两个明确的工作模式，不能在同一轮中混在一起。

### 9.1 模式一：完整故事适配

作者输入：

```text
Batch / 发现地点：
从头到尾的完整原始故事：
设备不可改变的外观与功能：
故事中明确是“相信 / 据说 / 可能”的部分：
目前刻意不知道的部分：
AI 不得修改或新增：
```

AI 按以下顺序输出：

1. **原稿复述**：用更清楚但不改变含义的方式复述一次；
2. **四个核心**：设备特征、来源线索、修复矛盾、叙事钩子；
3. **事实边界**：已确认、当前判断、刻意未解；
4. **内容发动机**：用一句因果链说明故事为何可以持续；
5. **四阶段节奏**：每阶段最多三个必要事件和一个进入条件；
6. **最少互动**：默认不投票；确有真实选择时最多先提出一个；
7. **作者确认问题**：只问会实质改变故事的少量问题。

这一步禁止生成完整内容节点表、完整帖子正文、多套投票或擅自补写结局。输出应保持短而可审阅。

### 9.2 模式二：已批准故事的发布拆解

故事适配稿经作者确认后，AI 才接收具体发布任务。每次任务至少提供：

```text
Batch：
当前状态：
目标内容类型：
目标读者：公开访客 / 关注者 / 持有者
上一个已发布节点：
本次新事实：
仍待验证的信息：
受影响的 Pack 或日期：
用户需要采取的行动：
必须回收的旧问题：
允许使用的角色：
可用影像：
禁止新增或修改的事实：
期望长度：
```

### 9.3 发布内容的 AI 生成顺序

1. 复述本次不可修改的事实；
2. 指出缺失且无法合理推断的信息；
3. 先写内容结构，不立即写气氛化正文；
4. 生成首稿；
5. 对照连续性账本检查数字、日期和角色；
6. 标出所有新增假设；
7. 由编辑确认后进入发布稿。

### 9.4 AI 必须遵守

- 不自行创造价格、库存、日期、物流或售后政策；
- 不擅自增加 Pack；
- 不把故事适配任务自动扩大成完整内容计划；
- 不改变作者原稿的核心前提、因果关系和结尾钩子；
- 不把估计写成已确认；
- 不把“我们相信”“据说”“似乎看到”改写成平台已证实；
- 不让 NPC 冒充真实成员；
- 不为增强戏剧性制造安全事故、丢件或延期；
- 不引用连续性账本之外的“既往事件”；
- 不为提高参与度而强行添加投票；
- 信息不足时留下明确占位或提出问题，而不是补全事实。

## 11. 发布前检查清单

### 事实

- [ ] 价格、数量、日期和 Pack 内容来自最新事实账本；
- [ ] 已确认、估计和待验证被清楚区分；
- [ ] 没有新增未经授权的商业承诺；
- [ ] 状态与实际行动一致；
- [ ] Console 所在 Pack 清楚可见。

### 连续性

- [ ] 承接了明确的上一节点；
- [ ] 没有与既往内容冲突；
- [ ] 新问题已经登记回收节点；
- [ ] 投票或旧问题的结果得到体现；
- [ ] 人物、地点和物件名称保持一致。

### 用户价值

- [ ] 用户能在前两句话知道发生了什么；
- [ ] 能看出这条内容为什么现在发布；
- [ ] 能理解它对 Pack、Console 或等待时间的影响；
- [ ] 如果需要行动，只突出一个主要行动；
- [ ] 没有用长篇介绍重复页面已有信息。

### 语气

- [ ] 使用具体动作和证据；
- [ ] 删除无信息量的神秘形容词；
- [ ] 没有堆叠假代码、假坐标和“机密”警告；
- [ ] 商业信息直接而清楚；
- [ ] 角色声音稳定但没有妨碍理解。

### 影像

- [ ] 图片或视频与本次事件直接相关；
- [ ] 媒体有日期、主体和说明；
- [ ] 多图顺序能形成观察过程；
- [ ] 复原、示意或生成素材的性质已正确登记；
- [ ] 没有把成员投稿伪装成组织现场证据。

## 12. 编辑评分标准

每条重要内容发布前可以按 100 分评估：

| 维度 | 分值 | 判断 |
|---|---:|---|
| 事实准确 | 25 | 商业、履约、数字和状态无误 |
| 连续因果 | 20 | 承接旧事件并明确推进下一节点 |
| Batch 独特性 | 15 | 不能无损替换成另一个地点和名称 |
| 用户价值 | 15 | 用户知道发生什么、影响什么、要做什么 |
| 角色一致 | 10 | 发言符合固定职责和声音 |
| 媒体证据 | 10 | 影像真正补充或证明内容 |
| 文案克制 | 5 | 简洁、具体、没有装饰性噪音 |

任何涉及价格、数量、日期、Pack 内容或物流的事实错误，无论总分多少都不能发布。

## 13. 一个最小因果链示例

以下示例只展示结构，不代表真实 Batch：

1. **首次发现**：现场发现 28 台设备，其中两组天线接口不同；
2. **探测更新**：测试确认接口差异会改变接收方向；
3. **开放申领**：确认 24 台可恢复，并公布四个 Pack；
4. **Pack 01**：成员收到各自设备对应的接口拓印和现场编号卡；
5. **成员参与**：持有者投票决定优先公开哪一组接收方向的测试；
6. **结果回收**：负责人发布获选方向的测试视频，并说明另一方向仍继续验证；
7. **Pack 02**：成员收到与获选测试对应的天线零件和记录；
8. **Console 出货**：Unit 根据接口类型完成分配，成员此前收到的记录能够对应自己的设备；
9. **运行档案**：持有者比较不同地区的首次信号，原有接口问题转化为长期观察主题。

这条链条的价值在于：现场发现、成员决定、实体 Pack、Unit 分配和到手后的使用记录属于同一个故事，而不是九条互不相关的内容。

---

## 14. 最终判断

一份合格的 Batch 内容计划应同时满足：

- 没有故事，它仍是一份清楚可信的产品与履约记录；
- 没有购买按钮，它仍是一段值得持续关注的行动档案；
- 每个 Pack 都能解释自己为何存在；
- 每次成员参与都能在后续看见结果；
- Console 到手时，用户能回头理解此前所有内容如何共同抵达这一刻；
- 进入运行中后，这个 Batch 仍然拥有继续被记录的理由。

写作者的任务不是不断制造神秘，而是让一个 Batch 在时间中留下可信、连续、可共同参与的历史。
